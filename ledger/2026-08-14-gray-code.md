## Threads, scheduled thread (slides 01–04 JPEG on item 1, link in the LAST item)
Scheduled `2026-08-14T17:00:00Z` (18:00 Europe/London, BST) · postId `cmsst6acr00qos30ys5qjjsmc` · `state: QUEUE`.

1. watch an ordinary binary counter tick from three to four. it reads 0111, then all at once 1000, four wires flipping in a single step. on paper the number just went up by one. but the wires do not switch at the same instant, and for a sliver of time the counter shows neither number. read it right then and you read a count that never existed. *(4 JPEGs attached here)*
2. that is not a rare glitch at the edges. it is how ordinary counting moves: roughly every other step flips more than one bit, and the worst steps flip all of them. the value is always right once things settle. it is the transitions that lie. gray code is the fix, and it is almost impossibly clean.
3. keep the same whole numbers, 0 up to 2^w - 1, but put them in a new order where any two neighbours differ in exactly one bit. not usually one. always one. there is no in-between pattern to misread, because there is no in-between: the counter is either fully in its old state or fully in its new one. and the whole recipe is one line, gray(t) = t xor (t >> 1).
4. why only one bit? build the list by writing it out, then writing it again upside down beneath, a 0 in front of the top half and a 1 in front of the mirror. every join still costs one flip, even the seam in the middle. because neighbours differ in one bit, the order is a single loop that visits every corner of the w-dimensional cube exactly once. a hamiltonian cycle, for free, from one line of arithmetic.
5. this is why rotary and position encoders are cut in gray code. skew the sensors on a binary disc and at a boundary it flashes a phantom, a number it is neither leaving nor entering. gray cannot: adjacent sectors differ in one band, so the only thing a misread sensor can disagree about is whether that one band has turned yet, and both answers are honest. frank gray, bell labs, patent 1953.
